`show` commands tell you the state of a device right now. The tools on this page tell you what happened, what is happening to individual packets, and how things change over time. Each has a cost, in CPU, in effort or in blind spots, and a good engineer picks the cheapest tool that answers the question.

## Logs

A device writes *syslog* messages whenever something noteworthy happens: a link changes state, a neighbor goes away, a configuration is saved. Each message has a severity from 0 to 7. A lower number is more urgent.

| Number | Name | Example |
| --- | --- | --- |
| 0 | Emergencies | System unusable |
| 1 | Alerts | Immediate action needed |
| 2 | Critical | Critical condition |
| 3 | Errors | `%LINK-3-UPDOWN` interface down |
| 4 | Warnings | `%CDP-4-NATIVE_VLAN_MISMATCH` |
| 5 | Notifications | `%LINEPROTO-5-UPDOWN`, `%SYS-5-CONFIG_I` |
| 6 | Informational | Normal events |
| 7 | Debugging | Output from `debug` commands |

The severity is the number between the dashes in the message name. `logging buffered` keeps messages in RAM, and `show logging` prints them. By default the console shows messages, but a session over SSH does not. Type `terminal monitor` to see them live in your session.

```console S1
S1# terminal monitor
S1# show logging | include UPDOWN
Oct  8 09:11:40.301: %LINK-3-UPDOWN: Interface GigabitEthernet0/1, changed state to down
Oct  8 09:11:41.305: %LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/1, changed state to down
```

Messages can also be sent to a syslog server with `logging host 10.1.1.80`, so they survive a reboot and can be searched across many devices. That works only if every device's clock is right.

## Debug

`debug` makes a device print what its software is doing, packet by packet or event by event. It is the most detailed view and the most dangerous. Debugging output is generated by the CPU, and a broad debug on a busy router can raise CPU use until the device stops responding, even to your own session.

Rules for using it safely:

- Use the narrowest debug that answers your question, such as `debug ip ospf adj`, not `debug ip packet`.
- Limit it where you can, for example with an ACL that matches one host.
- Watch for the output with `terminal monitor`, then turn it off the moment you have the answer.
- Stop everything with `undebug all` (or `no debug all`).

```command
prompt = "You have finished debugging. Turn off every debug at once."
mode = "R1#"
answer = ["undebug all", "no debug all"]
why = "Leaving a debug running keeps loading the CPU. Turn it off as soon as you have what you need."
```

## Packet capture

Sometimes only the packets will do: what exactly did the client send, and what came back? Two approaches are common.

**SPAN** (switched port analyzer) tells a switch to copy traffic from one port to another, where a PC runs a capture tool such as Wireshark.

```console S1
S1(config)# monitor session 1 source interface gigabitEthernet 0/1
S1(config)# monitor session 1 destination interface gigabitEthernet 0/24
```

Gi0/1 is the port under study, and Gi0/24 is where the analyzer is plugged in. The destination port stops behaving like a normal access port while the session runs.

**Embedded Packet Capture** on IOS XE captures on the device itself, using `monitor capture` commands, and can export a file for Wireshark.

Either way, keep a capture short and filtered. Large captures are hard to read and slow to move.

## Monitoring over time

Some problems only show up as trends, and no `show` command will catch a problem that happened last night.

- **SNMP** lets a management system poll devices for counters such as interface load and errors, and receive traps. It produces the graphs and the baseline.
- **NetFlow** records which addresses and ports are talking and how much, so it answers "who is using the link?"
- **IP SLA** makes a device send its own probes on a schedule and record results.

```console R1
R1(config)# ip sla 1
R1(config-ip-sla)# icmp-echo 10.9.9.9 source-interface GigabitEthernet0/0/0
R1(config-ip-sla-echo)# frequency 30
R1(config-ip-sla-echo)# exit
R1(config)# ip sla schedule 1 life forever start-time now
```

`show ip sla statistics` then gives you the success and round-trip time of a probe sent every 30 seconds, whether or not anyone is watching.

## Physical tools

For cabling, a handheld *cable tester* finds opens, shorts, split pairs and wiremap errors, and certifiers measure whether a run meets its category. Many switches can test a copper port themselves. `test cable-diagnostics tdr interface gigabitEthernet 1/0/1` uses time-domain reflectometry to find a break and its approximate distance; the result is read with `show cable-diagnostics tdr interface gigabitEthernet 1/0/1`. Support depends on the platform.

## Choosing a tool

| Tool | Shows | Use it for | Cost |
| --- | --- | --- | --- |
| `show` commands | State right now | Almost everything first | None |
| Syslog | Events with time | What changed and when | Needs correct clocks |
| Debug | Software decisions | Why a protocol fails | CPU load; can freeze a device |
| SPAN with Wireshark | Actual packets | Exactly what is on the wire | Needs a spare port and a PC |
| Embedded capture | Packets on the device | Capture without extra hardware | Platform support; CPU |
| SNMP / NetFlow | Trends and top talkers | Baselines, slow links | Setup work |
| IP SLA | Scheduled probes | Continuous reachability | Small, configured per probe |
| Cable tester / TDR | Physical wiring | Copper faults | Needs access to the cable |
