A user phones: "the internet is down." The tempting move is to start changing things, rebooting the router or swapping a cable. Sometimes that works. When it does not, you have changed three things, you do not know which mattered, and you cannot undo any of them with confidence. A fixed method keeps you from that. It is slower for the first minute and faster for the rest.

## Six steps

1. **Identify the problem.** Gather facts and state the problem in one sentence.
2. **Establish a theory of probable causes.** Start with the likeliest and the cheapest to check.
3. **Test the theory.** Run a check that would prove it wrong. If it fails, form a new theory. If you are out of ideas, escalate.
4. **Establish a plan of action and implement it.** Make one change at a time, and know how to undo it.
5. **Verify the solution.** Confirm that the original symptom is gone and that nothing else broke. Add preventive measures if they are cheap.
6. **Document findings, actions and outcomes.** The next person, who may be you in six months, will meet this problem again.

## Asking users

Step one depends on what the user can tell you, and users describe symptoms, not causes. Ask short, specific questions.

- What exactly happens? Which message appears?
- Who else is affected? One PC, one floor, everyone?
- Did it ever work? When did it stop?
- What changed: a new device, a moved cable, an update?

"Only me, since the move on Monday" points at a cable or a port. "Everyone, since 9 am" points at something shared, such as the router, a server or the internet link.

```question
prompt = "Only one PC cannot reach the server, and every other PC can. Which theory deserves testing first?"
options = ["The server has failed", "The internet link is down", "A fault on that PC, its cable or its switch port", "The core switch has failed"]
answer = 2
why = "If everything else works, the shared parts are working. The fault lies in what is unique to the failing PC."
```

## Choosing where to start

Step two has several well-known approaches.

| Approach | How it works | Good when |
| --- | --- | --- |
| Bottom-up | Start at the physical layer and move up | You suspect cabling or hardware |
| Top-down | Start at the application and move down | The problem seems to be one program |
| Divide and conquer | Test a middle layer, then go up or down | You have no strong suspicion |
| Educated guess | Pick the cause from experience | You have seen this exact symptom before |

A guess that is wrong costs little if you then fall back on a structured approach.

## When to escalate

Escalate when you have exhausted your theories, when the fix needs access you do not have, or when company policy says a certain type of fault goes to a senior technician or to the vendor's support. Hand over what you found, not only the complaint: the symptoms, the tests you ran and the results. Escalating with notes is part of doing the job well.

## Watching events with debug

Show commands display a state at one moment. `debug` commands print events as they happen. `debug ip icmp` prints each ICMP message the router sends or receives, which is useful when a ping seems to vanish and you want to see whether the reply arrived. First make the timestamps useful, then turn the debug on and ping.

```console R1
R1# configure terminal
R1(config)# service timestamps debug datetime msec
R1(config)# end
R1# debug ip icmp
ICMP packet debugging is on
R1# ping 192.168.1.10
Type escape sequence to abort.
Sending 5, 100-byte ICMP Echos to 192.168.1.10, timeout is 2 seconds:
*Oct  8 09:14:22.101: ICMP: echo reply rcvd, src 192.168.1.10, dst 192.168.1.1, topology BASE, dscp 0 topoid 0
...
!!!!!
Success rate is 100 percent (5/5), round-trip min/avg/max = 1/1/2 ms
```

The `*` in front of the time means the router's clock is not synchronized. Wording varies between IOS releases, and the router prints one such line per reply, so the example is trimmed to one.

```trap
Debug output is generated by the CPU, and a busy router can print so much that it becomes slow or unreachable. Use narrow debugs, never `debug all` on a production device, and turn them off when you have your answer.
```

Stop debugging with `undebug all` (or `no debug all`).

```command
prompt = "Turn off every debug that is running."
mode = "R1#"
answer = ["undebug all", "no debug all"]
why = "undebug all disables all debugging at once, which is the quick way to stop output and CPU load."
```

## Seeing output over SSH

Debug and log messages go to the console by default (`logging console` controls that). In an SSH or Telnet session you see nothing until you type `terminal monitor`. Use `terminal no monitor` to stop the flow when you are done.

```recall
front = "What are the six troubleshooting steps, in order?"
back = "Identify the problem, theorize causes, test the theory, plan and implement, verify, document."
```

