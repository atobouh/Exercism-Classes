Proposal for OctetThe lab, rebuilt as a kitOctober 2026

Octet Lab SDK

The network lab you already have, packaged so any course site can drop a live lab onto a page with one tag. The engine is the Rust simulator, compiled to run in the browser. The map gets its own drawn device glyphs instead of boxes.

The router-on-a-stick lab that ships today, redrawn with the proposed glyphs. The card outline and the badge on R1 come from the simulator's fault report.

What this is for

Today the lab lives inside Octet. The simulator is a Rust crate, the map and console are Octet's own JavaScript, and a lab is a TOML file. That works for you. It can't leave the app.

The proposal is to split it into a small kit with a clear edge, so the same lab runs in three places without changes: inside Octet, embedded in any course page, and headless in a test or a grader. Octet becomes the kit's first customer instead of its only home.

The kit, layer by layer

Each layer only talks to the one below it. A course site can stop at whichever layer it needs: the whole drop-in element, the engine with its own interface, or just the lab files.

Your page

Octet, a Moodle or Canvas course, a static docs site, a blog post. It places the element and listens for events.

any HTML page

The lab element

<octet-lab>, a web component in its own shadow DOM. Map, console, ports, changes and checks, themed with CSS variables. No framework required, so it works next to React, Vue or nothing.

@octet/lab-element

Glyphs

The device icon set as an SVG sprite and as individual files, with states for selected, fault and powered off. Usable on its own in slides and diagrams.

@octet/glyphs

The engine API

A small JavaScript API around the simulator: load a lab, type into a device, run the checks, snapshot and restore, listen for changes. It has no interface of its own.

@octet/lab

The simulator

The existing octet-sim Rust crate: VLANs, trunks, subinterfaces, routing, the IOS-style console, fault finding. It compiles to WebAssembly for the browser and links natively into the desktop app.

octet-sim · octet-sim.wasm

The lab format

A published, versioned spec for lab files: devices, cables, starting configs, the brief, tasks and checks, hints. Course authors write these by hand or with the prompt from Settings.

*.lab.toml · format 1

Using it from a course site

The common case is one script and one tag. Everything runs in the student's browser, so the course site needs no server and no account with anyone.

Drop-in element 
<!-- once per page -->
<script type="module" src="/vendor/octet-lab.js"></script>

<octet-lab
  src="/labs/router-on-a-stick.lab.toml"
  theme="auto"
  panels="map console checks"></octet-lab>

<script>
  const lab = document.querySelector('octet-lab')
  lab.addEventListener('lab-passed', e =>
    myCourse.markDone(e.detail.lab, e.detail.tasks))
</script>
Engine only, with your own interface 
import { loadLab } from '@octet/lab'

const lab = await loadLab(await (await fetch(url)).text())

lab.exec('R1', 'conf t')
lab.exec('R1', 'int g0/0/1.20')
const r = lab.exec('R1', 'encap dot1q 20')
r.output      // what the device printed
lab.fault()   // { device, iface, message } or null
lab.checks()  // [{ task, pass, hint }]
lab.on('change', view => redraw(view))
const saved = lab.snapshot()   // JSON, yours to store

Saving is the host's choice. By default the element keeps progress in the browser. A course site that wants progress on its own server passes a store with load() and save(snapshot), and the lab never needs to know where it went.

Glyphs, not boxes

Each device is drawn as its real shape, then given one mark that says what it does:

  • Rack gear (switches, routers, firewalls, controllers, servers) gets a faceplate with rack ears, the detail that makes it read as equipment.
  • Endpoints are their own silhouettes.
  • Wireless radiates.
  • Anything outside your network is a contour, never a box.

All glyphs share a 32-unit grid, one stroke weight and one corner radius, so they sit together on a map. They take the current text colour, so they work in both themes and in a course site's own palette.

Cables and states carry meaning

The map keeps Octet's colour rules. Green is you, red is broken, and everything else is ink. A cable's line style says what kind of link it is, and a small mark at the port end says what that port is doing, so a student can read spanning tree or a shut interface straight off the map.

Copper or fibreA plain line. Fibre is thinner, with a light inner core.
TrunkA double rule, labelled with the VLANs it allows.
SerialThe WAN zig, mid-span.
WirelessA dotted line between a client and its access point.
BlockingA bar across the port end: spanning tree is holding this port.
DownDashed and red, with a dot on the side that's down.

Three kinds of lab, one format

You asked for a mix of console, building and fixing. Each is a way of setting up the same file, not a separate product.

KindThe student starts withPasses when
ConfigureThe devices cabled, with blank or partial configsThe checks pass: pings, VLANs, trunks, routes
Fix itA working network with faults planted in the starting configThe fault report is clear and every check passes
BuildAn empty canvas and a parts listThe required devices and cables exist and the checks pass
 
# router-on-a-stick.lab.toml (format 1, as it reads today plus three new keys)
format = 1
id = "srwe-03-router-on-a-stick"
title = "Router-on-a-stick"
kind = "fix"                      # configure | fix | build

[[device]]
name = "R1"
kind = "router"
model = "ISR4321"
config = """
interface g0/0/1.20
 encapsulation dot1q 30           # the planted fault
"""

[[task]]
text = "PC-SALES can ping PC-ENG"
check = { ping = { from = "PC-SALES", to = "192.168.20.10" } }
hint = "Look at the tag on R1's .20 subinterface."

What the simulator does now, and next

The engine is honest about its edges. A command it doesn't know gets a real IOS error and a pointer to the supported list, so a student never learns something false.

AreaStatusCovers
SwitchingWorks todayVLANs, access and trunk ports, native VLAN, allowed lists
RoutingWorks todayConnected and static routes, subinterfaces, gateways, ping with the reply path
ConsoleWorks todayModes, abbreviations, ? help, IOS error messages, PC commands
Spanning treePhase 3Root election, port roles, Rapid PVST+, PortFast and BPDU guard
ServicesPhase 3DHCP server and relay, NAT and PAT, standard and extended ACLs
OSPFPhase 4Single-area OSPFv2: neighbours, DR/BDR, cost
IPv6Phase 4Addressing, SLAAC, static routes

How it gets built

Phase 1

Split the engine out

Compile octet-sim to WebAssembly and wrap it in the @octet/lab API. Octet's desktop app keeps the native build. The existing tests run against both builds, so they can't drift apart.

Phase 2

The element and the glyphs

Move the map, console and checks out of Octet's app code into <octet-lab>. Draw the full glyph set with its states. Then switch Octet to use the element itself, which proves the kit works on a real product.

Phase 3

The format and the first protocols

Publish the lab format spec with a validator, the same way octet-check validates pages. Add spanning tree, DHCP, NAT and ACLs, with a lab for each.

Phase 4

Ready for other people's sites

A documentation page with live examples. A lesson-tracker adapter (SCORM and xAPI) for course platforms. OSPF and IPv6. The GNS3 bridge from the roadmap fits here too, as another engine behind the same API.

What I need from you

These decisions change what gets built, so they're yours.

Open source or private?Making the kit open source (MIT or Apache-2.0) is what makes "someone could port it to their course site" real. Keeping it private keeps it yours alone. I'd suggest open-sourcing the simulator and the element, and keeping Octet's books and app private.
The name"Octet Lab" ties the kit to the app. A separate name would let it stand on its own if it's going to be used outside Octet.
Which protocols come first in phase 3My order would be spanning tree, then ACLs, then NAT, then DHCP, because that's roughly where the books need labs most. If your course is somewhere else, the order should follow it.
The glyph directionThe faceplate-and-mark style above is the proposal. If it feels right, I'll draw the full set, with port-level detail for the console panel. If not, tell me which glyphs miss.
